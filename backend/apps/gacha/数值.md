# MotiWish 交易系统 V1 数值方案

## 0. 2026-06-05 修订：日常指标不是任务

前端页面中的“今日日常指标”不再视为任务模板，也不需要“制定日常”的 API。它是每日生活状态监控奖励，由用户提交当天起床时间、睡觉时间、手机使用时长、饮水杯数后，服务端 Agent 结合用户画像、当天状态和近期历史，直接给出反馈与一级货币奖励。

### 0.1 日常指标输入

- 起床时间：`HH:MM`
- 睡觉时间：`HH:MM`
- 手机使用时长：分钟
- 饮水杯数：整数

### 0.2 奖励范围

日常指标奖励是轻量生活反馈，不等同于任务完成奖励。V1 推荐范围：

- 最低：`0` 一级货币
- 最高：`40` 一级货币
- 良好日常通常落在 `20 - 35`
- 非常健康且较近期有改善时，可到 `40`

该范围低于大型任务奖励，避免用户通过生活记录刷出过量一级货币，同时保留每日正反馈。

### 0.3 历史保留与压缩

- 7 天内：保留完整日常记录、Agent 反馈、画像快照和评估上下文。
- 7-30 天：保留必要指标、分数和奖励，清理长上下文，并生成近期摘要。
- 30 天-1 年：以月度 Agent 摘要保存趋势，删除日级明细。
- 1 年前：删除明细和摘要，不再保存。

### 0.4 与任务系统的关系

原文中“日常任务”的表述应理解为历史设计口径。新实现中，日常生活指标不通过任务创建/任务结算接口处理，而通过独立的 `POST /api/v1/daily/evaluate/` 完成评估与奖励发放。周期性学习、健身、阅读等仍应使用周期任务。


## 1. 设计目标

本方案服务于以下业务闭环：

- 完成任务，获得一级货币
- 消耗一级货币抽卡，获得二级货币
- 消耗二级货币兑换愿望商品

设计原则：

- 一级货币是“行为反馈货币”
- 二级货币是“长期积累货币”
- 抽卡需要提供惊喜感，但不能破坏经济稳定
- 所有扣费、发奖、保底、利息结算均由服务端统一处理

## 2. 货币职责

- 一级货币：只进入抽卡系统
- 二级货币：只进入商店兑换
- 一级货币不直接兑换愿望
- 二级货币不反向兑换一级货币

## 3. 抽卡系统

### 3.1 单抽消耗

- 单抽消耗：`50` 一级货币

### 3.2 四档奖励

参考优化提案，V1 建议从“三档”微调为“四档”，保留整体期望稳定的同时，引入极低概率的大额惊喜档，增强抽卡的情绪价值。

推荐奖励如下：

1. 普通档
- 概率：`72%`
- 获得：`5` 二级货币

2. 优秀档
- 概率：`20%`
- 获得：`20` 二级货币

3. 暴击档
- 概率：`6%`
- 获得：`40` 二级货币

4. 传说档（SSR/UR）
- 概率：`2%`
- 获得：`200` 二级货币

### 3.3 期望值

单抽平均收益：

- `0.72 * 5 + 0.20 * 20 + 0.06 * 40 + 0.02 * 200`
- `= 3.6 + 4 + 2.4 + 4`
- `= 14.0`

即：

- `50` 一级货币 -> 平均 `14` 二级货币
- 平均比例约为 `3.57 : 1`

说明：

- 普通、优秀、暴击三档仍然维持日常稳定收益
- 新增传说档后，用户会保留“一发入魂”的预期
- 由于传说档概率仅 `2%`，整体经济仍可控

## 4. 保底机制

### 4.1 小保底

- 连续 `10` 抽没有出现“优秀档”或“暴击档”
- 第 `11` 抽保底获得 `20` 二级货币

### 4.2 大保底

- 连续 `30` 抽没有出现“暴击档”
- 第 `31` 抽保底获得 `40` 二级货币

### 4.2.1 传说保底

- 连续 `80` 抽没有出现“传说档”
- 第 `81` 抽保底获得 `200` 二级货币

### 4.3 保底说明

- 小保底用于避免长期只出普通档
- 大保底用于避免长期不出中高收益档
- 传说保底用于保护极端非酋用户的长期体验
- `10 / 30 / 80` 的节奏既保留惊喜，也不会让 SSR 过于泛滥

## 5. 一级货币产出建议

为了匹配 `50` 一级货币单抽成本，任务奖励建议统一成 `5` 或 `10` 的倍数。

### 5.1 日常任务

- 轻量日常：`10 - 20`
- 中等日常：`20 - 40`
- 重点日常：`50 - 60`

示例：

- 按时起床：`10`
- 控制手机时长达标：`15`
- 背单词 30 分钟：`20`
- 完成专注学习 90 分钟：`40`
- 全天健康习惯全达标：`60`

### 5.2 周期任务

- 每日周期任务：`20 - 40`
- 每周任务：`60 - 150`
- 每月任务：`200 - 500`

#### 5.2.1 周期任务奖励设计目标

周期任务和一次性任务不同，它的核心不是“赶在某个 ddl 前冲刺”，而是：

- 持续执行
- 稳定打卡
- 对周/月计划形成节奏感

因此周期任务奖励建议由三部分构成：

- 基础奖励
- 完成率奖励
- 连续完成加成

#### 5.2.2 周期任务奖励总公式

定义：

- `B`：周期任务基础奖励
- `c`：本周期内实际完成次数
- `n`：本周期内应完成次数
- `r`：周期完成率，`r = c / n`
- `S`：连续完成加成系数

最终奖励公式：

- `RecurringReward = round_5(B * F_cycle(r) * S)`

其中：

- `round_5(x)` 表示四舍五入到最接近的 `5`
- `F_cycle(r)` 表示完成率系数

#### 5.2.3 完成率系数

建议采用分段线性函数：

1. 当 `0 <= r < 0.5`

- `F_cycle(r) = 0.8 * r`

2. 当 `0.5 <= r < 0.8`

- `F_cycle(r) = 0.40 + 1.0 * (r - 0.5)`

3. 当 `0.8 <= r <= 1.0`

- `F_cycle(r) = 0.70 + 1.5 * (r - 0.8)`

关键点：

- `r = 0.0` 时，系数 `0.00`
- `r = 0.5` 时，系数 `0.40`
- `r = 0.8` 时，系数 `0.70`
- `r = 1.0` 时，系数 `1.00`

解释：

- 完成率低于一半时，奖励增长较慢
- 完成一半后，用户开始有“这周还算坚持住了”的回报
- 接近满勤时，奖励增长更快，鼓励把最后几次也做完

#### 5.2.4 连续完成加成

为了鼓励习惯养成，建议再叠加连续完成加成：

- 连续完成 `3` 个周期：`S = 1.05`
- 连续完成 `7` 个周期：`S = 1.10`
- 连续完成 `14` 个周期：`S = 1.15`
- 连续完成 `30` 个周期：`S = 1.20`

说明：

- 这里的“周期”对不同任务不同
- 日任务按“天”计
- 周任务按“周”计
- 月任务按“月”计

建议上限：

- `S <= 1.20`

这样既有持续激励，也不至于把奖励膨胀得太高。

#### 5.2.5 三类周期任务建议基准

##### A. 每日周期任务

适合：

- 背单词
- 跑步
- 阅读
- 晚间复盘

基础奖励建议：

- 轻量每日任务：`20`
- 中量每日任务：`30`
- 重量每日任务：`40`

结算方式建议：

- 按“当天完成即得”发放
- 若你们想加强周节奏，也可以额外增加“周满勤奖”

推荐补充：

- 连续完成 `7` 天，额外奖励 `20`
- 连续完成 `14` 天，额外奖励 `50`
- 连续完成 `30` 天，额外奖励 `100`

##### B. 每周周期任务

适合：

- 每周健身 3 次
- 每周完成一次课程复盘
- 每周整理一次房间

基础奖励建议：

- 轻量周任务：`60`
- 中量周任务：`100`
- 重量周任务：`150`

结算方式建议：

- 不建议每完成一次就全额发放
- 更推荐按“本周完成率”统一结算

例子：

若某周任务要求一周完成 `4` 次，基础奖励 `B = 100`

- 完成 `1/4`：
  - `r = 0.25`
  - `F_cycle = 0.20`
  - 奖励约 `20`
- 完成 `3/4`：
  - `r = 0.75`
  - `F_cycle = 0.65`
  - 奖励约 `65`
- 完成 `4/4`：
  - `r = 1.0`
  - 奖励 `100`

##### C. 每月周期任务

适合：

- 每月读完一本书
- 每月完成若干次系统性训练
- 每月稳定打卡达到一定次数

基础奖励建议：

- 轻量月任务：`200`
- 中量月任务：`300`
- 重量月任务：`500`

结算方式建议：

- 按“月完成率”统一结算
- 月任务通常目标大、周期长，因此建议奖励波动也更明显

例子：

若某月任务基础奖励 `B = 300`

- 完成率 `50%`：
  - 奖励约 `120`
- 完成率 `80%`：
  - 奖励约 `210`
- 完成率 `100%`：
  - 奖励 `300`

#### 5.2.6 周期任务失败惩罚建议

周期任务惩罚建议比一次性任务更轻，因为它强调习惯维持而不是一次性成败。

定义：

- `Q`：周期任务基础惩罚
- `r`：完成率

建议公式：

- `RecurringPenalty = round_5(Q * (1 - r)^1.1)`

推荐惩罚基准：

- 每日周期任务：`5 - 10`
- 每周周期任务：`10 - 30`
- 每月周期任务：`30 - 60`

解释：

- 完成率越高，惩罚越小
- 周期任务的主要导向应是“多做多得”，而不是“少做重罚”

### 5.3 一次性任务

- 小型一次性任务：`30 - 80`
- 中型一次性任务：`100 - 250`
- 大型一次性任务：`300 - 800`

## 6. 一次性任务奖惩机制

一次性任务建议由服务端结合三项因素统一结算：

- 任务基础价值
- 完成进度
- 是否超时

本方案中：

- 奖励采用“分段线性”公式
- 惩罚采用“进度折减惩罚 + 负债利息”机制

### 6.1 奖励机制

#### 6.1.1 奖励总公式

定义：

- `R`：任务基础奖励，单位为一级货币
- `p`：完成进度，范围 `0 <= p <= 1`
- `F_progress(p)`：进度奖励系数
- `F_time`：时间奖励系数

最终奖励公式：

- `Reward = round_5(R * F_progress(p) * F_time)`

其中：

- `round_5(x)` 表示四舍五入到最接近的 `5` 的倍数

#### 6.1.2 进度分段线性函数

建议使用如下分段线性函数：

1. 当 `0 <= p < 0.3`

- `F_progress(p) = 0.5 * p`

2. 当 `0.3 <= p < 0.8`

- `F_progress(p) = 0.15 + 0.9 * (p - 0.3)`

3. 当 `0.8 <= p <= 1`

- `F_progress(p) = 0.60 + 2.0 * (p - 0.8)`

关键点：

- `p = 0.0` 时，系数 `0.00`
- `p = 0.3` 时，系数 `0.15`
- `p = 0.8` 时，系数 `0.60`
- `p = 1.0` 时，系数 `1.00`

解释：

- 前 30% 进度奖励较低，防止“只做一点点也拿很多”
- 30% 到 80% 区间平稳增长，鼓励持续推进
- 80% 到 100% 区间斜率更高，鼓励真正做完

#### 6.1.3 时间奖励系数

建议按完成时间分三档：

- 提前或准时完成：
  - `F_time = 1.00`
- 逾期 24 小时内完成：
  - `F_time = 0.80`
- 逾期超过 24 小时完成：
  - `F_time = 0.60`

#### 6.1.4 奖励示例

若任务基础奖励 `R = 200`：

1. 进度 `100%`，准时完成

- `Reward = round_5(200 * 1.00 * 1.00) = 200`

2. 进度 `90%`，准时完成

- `F_progress = 0.60 + 2.0 * 0.1 = 0.80`
- `Reward = round_5(200 * 0.80) = 160`

3. 进度 `60%`，准时完成

- `F_progress = 0.15 + 0.9 * 0.3 = 0.42`
- `Reward = round_5(200 * 0.42) = 85`

4. 进度 `100%`，逾期 24 小时内完成

- `Reward = round_5(200 * 1.00 * 0.80) = 160`

### 6.2 惩罚机制

#### 6.2.1 基础惩罚区间

- 小任务惩罚：`5 - 15`
- 中任务惩罚：`20 - 40`
- 大任务惩罚：`50 - 100`

原则：

- 惩罚应存在，但不应压过奖励本身
- 惩罚更多用于“提醒成本”，而不是“打击用户”

#### 6.2.2 超时惩罚公式

定义：

- `P`：任务基础惩罚，单位为一级货币
- `p`：完成进度，范围 `0 <= p <= 1`

若任务未超时：

- `Penalty = 0`

若任务超时：

- `Penalty = round_5(P * (1 - p)^1.2)`

解释：

- 完成进度越高，惩罚越低
- 用 `1.2` 次幂，让接近完成时惩罚下降更明显

#### 6.2.3 惩罚示例

若任务基础惩罚 `P = 50`：

1. `p = 0`

- `Penalty = round_5(50 * 1^1.2) = 50`

2. `p = 0.5`

- `Penalty ≈ round_5(50 * 0.5^1.2) ≈ 20`

3. `p = 0.8`

- `Penalty ≈ round_5(50 * 0.2^1.2) ≈ 5`

### 6.3 负代币机制

参考优化提案，不建议采用“时间复利滚雪球”的设计。对于个人管理应用，这会在用户现实压力较大时显著放大挫败感，增加流失风险。

因此 V1 建议改为：

- 保留有限负债
- 取消按天复利
- 引入“封顶债务 + 一次性重置代价”

#### 6.3.1 适用范围

- 仅对一级货币负余额生效
- 二级货币不允许为负
- 一级货币最低可到 `-100`

#### 6.3.2 债务规则

- 一级货币最低负债封顶：`-100`
- 到达 `-100` 后，不再继续向下扣减
- 后续任务失败只记录失败，不再追加经济惩罚

#### 6.3.3 负债恢复规则

建议一级货币收入优先用于还债：

1. 先冲减负债本金
2. 余额恢复为正后，剩余部分才进入可支配余额

#### 6.3.4 重置机制：休眠舱 / 破产重组

允许用户在现实压力过大时主动触发一次“重置”：

- 一级货币负债清零
- 连续完成 Buff 清零
- 周期任务连续完成加成清零
- 抽卡保底进度清零
- 扣除一笔固定重置成本，例如：
  - `50` 一级货币等价惩罚（若已为负则只记录一次重置状态）
  - 或冻结抽卡权限 `3` 天

推荐 V1 版本采用：

- 债务清零
- 抽卡保底进度清零
- 连续完成加成清零

这样既有惩罚，也给用户“重新开始”的台阶。

## 7. 商店定价建议

由于单抽平均约 `14` 二级货币，且存在低概率 `200` 的传说档，商店定价建议略上调，避免中小愿望被过快打穿。

### 7.1 小愿望

适合：

- 奶茶
- 小零食
- 30 分钟娱乐时间
- 一次轻度奖励

建议价格：

- `40 - 100` 二级货币

对应抽卡量：

- 约 `3 - 8` 抽

### 7.2 中愿望

适合：

- 一顿外卖
- 一本书
- 一场电影
- 一个小周边

建议价格：

- `120 - 300` 二级货币

对应抽卡量：

- 约 `9 - 23` 抽

### 7.3 大愿望

适合：

- 一个游戏
- 一次聚餐
- 一个中价位物品
- 一次短途活动预算

建议价格：

- `350 - 1000` 二级货币

对应抽卡量：

- 约 `28 - 73` 抽

## 8. 愿望商品来源

建议保留两种来源：

- 用户手动创建
- 系统推荐生成

### 8.1 用户手动创建

- 用户填写标题、描述
- AI 给出建议价格
- 服务端做价格边界裁剪后保存

### 8.2 系统推荐生成

- 依据用户画像、近期完成情况、目标标签刷新建议愿望
- 用户可关闭系统推荐
- 推荐内容应与用户画像和任务标签相关

## 9. AI 定价建议逻辑

AI 负责“建议价格”，服务端负责“最终价格”。

AI 输出建议：

- 建议档位
- 建议价格
- 定价理由
- 风险标签

服务端做边界裁剪：

- 小愿望最低：`30`
- 小愿望最高：`120`
- 中愿望最低：`100`
- 中愿望最高：`350`
- 大愿望最低：`300`
- 大愿望最高：`1200`

## 10. 任务结算双轨制建议

参考优化提案，建议将任务划分为两条结算轨道。

### 10.1 常规轨道

适用任务：

- 可明确量化进度的任务
- 线性推进的任务

例如：

- 背单词
- 健身
- 打扫房间
- 每周读书

常规轨道继续使用：

- 周期任务完成率公式 `F_cycle`
- 一次性任务进度公式 `F_progress`

### 10.2 探索轨道

适用任务：

- 科研
- 代码调试
- 创作
- 深度思考
- 黑盒型脑力劳动

特点：

- 进度难以精确量化
- 可能长时间投入但没有线性结果

建议采用按专注时长买断的结算方式：

- `ExplorationReward = round_5(T_focus * K_difficulty)`

定义：

- `T_focus`：有效专注时长，单位为小时
- `K_difficulty`：难度系数

建议难度系数：

- 轻度探索：`15`
- 中度探索：`25`
- 高强度探索：`40`

例子：

- 2 小时中度探索任务：
  - `Reward = round_5(2 * 25) = 50`
- 5 小时高强度探索任务：
  - `Reward = round_5(5 * 40) = 200`

这样可以保护“高脑力投入但不一定马上出结果”的任务体验。

## 11. 交易状态流建议

### 10.1 抽卡

1. 发起抽卡
2. 校验一级货币余额
3. 若存在负债，先检查是否达到负债下限
4. 扣除一级货币
5. 计算奖励档位与保底
6. 发放二级货币
7. 写入两条钱包流水
8. 写入抽卡记录
9. 全过程同事务

### 10.2 商店兑换

1. 发起兑换
2. 校验商品状态、库存、二级货币余额
3. 扣除二级货币
4. 生成兑换记录 `requested`
5. 兑现后改为 `fulfilled`
6. 若拒绝则 `rejected`

### 10.3 退款规则

建议：

- `rejected` 默认自动退款
- 退款时写逆向钱包流水

## 12. 用户体验节奏

按这套数值，用户大致会有如下感受：

- 一次任务完成会看到明显的一级货币上涨
- 几个轻量任务就能凑出一次抽卡
- 抽卡多数时候有基础收益
- 偶尔优秀档和暴击档带来惊喜
- 未完成任务会产生真实成本
- 若长期透支一级货币，会感受到债务压力，但不会被复利滚死
- 极低概率传说档能显著增强抽卡惊喜感
- 探索型任务不会因难以量化进度而被系统错误压制
- 小愿望可以短期达成，大愿望需要持续积累

## 13. V1 推荐参数汇总

### 抽卡

- 单抽成本：`50` 一级货币
- 普通档：`72% -> 5`
- 优秀档：`20% -> 20`
- 暴击档：`6% -> 40`
- 传说档：`2% -> 200`
- 小保底：连续 `10` 抽无优秀及以上，第 `11` 抽保底 `20`
- 大保底：连续 `30` 抽无暴击，第 `31` 抽保底 `40`
- 传说保底：连续 `80` 抽无传说，第 `81` 抽保底 `200`

### 一次性任务奖励

- 总公式：`Reward = round_5(R * F_progress(p) * F_time)`

### 周期任务奖励

- 总公式：`RecurringReward = round_5(B * F_cycle(r) * S)`

### 周期任务惩罚

- 总公式：`RecurringPenalty = round_5(Q * (1 - r)^1.1)`

### 一次性任务惩罚

- 超时惩罚公式：`Penalty = round_5(P * (1 - p)^1.2)`

### 负债机制

- 取消按天复利
- 一级货币最低允许：`-100`
- 允许主动触发一次“休眠舱 / 破产重组”重置

### 商店价格

- 小愿望：`40 - 100`
- 中愿望：`120 - 300`
- 大愿望：`350 - 1000`

### 探索轨道

- `ExplorationReward = round_5(T_focus * K_difficulty)`

## 14. 建议优先确认的关键点

建议优先确认以下事项：

1. 单抽是否固定为 `50` 一级货币
2. 三档奖励是否采用 `5 / 20 / 40`
3. 保底是否采用 `10 / 30`
4. 奖励分段线性公式是否采用当前这套斜率
5. 是否新增 `2%` 传说档（`200` 二级货币）
6. 是否接受取消复利，改为债务封顶 `-100`
7. 是否加入“休眠舱 / 破产重组”机制
8. 是否将任务结算拆成“常规轨道 + 探索轨道”
9. 商店三档价格是否采用 `40-100 / 120-300 / 350-1000`
